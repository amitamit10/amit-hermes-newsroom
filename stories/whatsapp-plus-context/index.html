Hermes WhatsApp Plus: context for the group, brakes for the bot

A native Hermes plugin adds bounded group history and explicit trust tiers; its voice-call branch is still an experiment.

Group chat is where a capable agent can fail socially: miss the setup, repeat itself, or keep answering until two bots drown out the room. WhatsApp Plus tries to make those failure modes explicit.

It wraps the platform; it does not fork Hermes

Hermes WhatsApp Plus describes itself as a native plugin, not a fork of Hermes Agent. It subclasses the stock WhatsApp adapter, registers through the plugin API, and generates its bridge from the current stock bridge with two hook insertions. If those hook anchors change upstream, the README says the plugin falls back to the stock bridge and raises an alert.[3]

That is a pragmatic maintenance strategy: keep the upstream bridge visible and add behavior around it instead of carrying a separate agent tree. The repository documents compatibility with Hermes 0.21.1 and `main` as of October 2026. The important caveat is right there too: future bridge changes can still change what the plugin can safely extend.[3]

Give the agent a slice of the room, not the whole year

When the agent is addressed in a group, the plugin can supply messages it has not seen yet, marked so the new context is distinguishable. The documented context can include a member roster, images, and voice-note transcripts. The project says group history is searchable for a year.[3]

That makes the useful unit of memory smaller than “replay every message.” The agent needs enough of the conversation to understand the question in front of it. The feature is not just recall; it is a policy about what gets stored, how the new slice is marked, and when the assistant is invited into the room.

Identity is not the same as permission

The plugin separates the owner, limited contacts, collaborating bots, temporary contacts, and strangers. Those roles do not receive identical capabilities. The README describes limited users as chat plus read-only tools, while also allowing them to ask the bot to message a phone number; collaborating bots are rate-limited and subject to a consecutive-reply cap.[3]

Groups the owner belongs to are allowed automatically but restricted to chat-only until approved from a private chat; the README also describes an exception when the owner and a limited user are both members. Strangers can be ignored or paired through a private flow. That is a more useful way to think about trust than a single allowlist: recognizing a sender is one question; deciding what that sender can make the agent do is another.[3]

Silence is a feature

For bot-to-bot rooms, the project documents a loop brake, automatic muting, a `[NO_REPLY]` silence path, and a pause control. It also lists explicit sending limits: 30 messages per hour and 10 new numbers per day, with random gaps for campaigns. The point is not to make the agent quieter for its own sake; it is to give it a clear way to stop participating.[3]

The plugin adds tools for messages, history, groups, delivery status, reactions, polls, pairing, and settings. Optional voice calls live in a separate component and are marked experimental; the voice README describes the patched calling engine as unofficial and fragile.[3][16]

The main README warns that WhatsApp can restrict personal-account automation if abused. The voice-call notes say WhatsApp can change the VoIP path and automated use may violate its terms; they recommend a number you can afford to lose, not a personal one.[3][16]

The repository publishes measurements—and labels their limits

The project includes timings from real calls, with numbers only and no conversation text in its metric file. In one answered call, three lookups—weather, opening hours, and shop checkout—started at the same time. Their recorded durations were 18.110, 23.814, and 34.498 seconds.[4][5]

Adding those durations gives 76.422 seconds, but that is arithmetic, not an observed sequential run. The longest measured lookup was 34.498 seconds, and each lookup was a full Hermes turn with tools—not voice-response latency. The chart above preserves those distinctions instead of turning one call into a grand performance claim.[4][5]

Voice is an experiment, not a benchmark

The same repository records a callback with two spoken answers averaging 346 milliseconds, with a 682-millisecond slowest answer, and a 98-second answered call with one answer at 963 milliseconds. That is three answers across two calls. The project's own voice-call README calls the sample small and says to read it as first measurements, not a benchmark.[4][16]

The component uses a patched copy of an upstream calling library as a second linked device, and its documentation calls the setup unofficial and fragile. The plugin is most interesting where it combines bounded group context, role-specific permissions, and a brake; the voice branch is a useful engineering experiment whose evidence should stay as modest as its sample.[16]
